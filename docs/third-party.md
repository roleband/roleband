# Third-party material

This page lists material in RoleBand that comes from somewhere else. It records
where each item comes from, its licence as the repository states it, and
whether RoleBand changed it. It is a record of facts and gives no legal
opinion. Ordinary package dependencies (`backend/requirements.txt`,
`dashboard/package.json`) are not listed unless their files are copied into
what RoleBand ships or runs.

Code and data copied or generated from an upstream source are pinned in
`backend/tracker/vendored.py` (repository, immutable ref, upstream path,
sha256, licence). `backend/scripts/check_vendored_upstream.py` compares each pin
with upstream, and `backend/tests/test_vendored_provenance.py` checks the
register. A new copied or generated artifact gets an entry there in the same
change. The apps' standalone Python is pinned in `launcher/macos/runtime.json` and
`launcher/windows/runtime.json`; `backend/scripts/check_runtime_python.py` reports a
pin behind python.org's newest release of its series, and
`backend/tests/test_runtime_python.py` checks the same against a copy of that list.
The embedded PostgreSQL and its pgvector are pinned by the `pixeltable-pgserver` wheel
and recorded in `backend/tracker/platform/pgcontrib/manifest.json`; the manifest's one
pgvector version, the source of the Linux and Windows bundles' portable library, is tested equal to the wheel's own. The
dependency audit cannot see them, because advisories name PostgreSQL, not the wheel.
`backend/scripts/check_embedded_postgres.py` reports a Postgres behind postgresql.org's
newest minor of its major (or a major no longer supported) and a pgvector behind the
newest patch of its series. When a newer minor of a supported major is out, it names the newest wheel and the
Postgres it builds, so the reader knows whether moving the wheel pin closes the gap.
`backend/tests/test_embedded_postgres_check.py` checks the verdicts against copies of
those lists. The wheel's Postgres 18 install is not checked: RoleBand does not run it.

App binaries are re-signed. The app includes explicit Postgres and checksum-pinned pgvector notices. |
| Prebuilt `pg_trgm` and portable pgvector | PostgreSQL 16.15 source archive from `ftp.postgresql.org`; pgvector 0.8.7 for Linux and Windows from its pinned source archive; source, wheel and bundle hashes in `backend/tracker/platform/pgcontrib/manifest.json` | PostgreSQL; each bundle carries the source's `COPYRIGHT`, which also contains pgvector's licence notice | Compiled bundles in `backend/tracker/platform/pgcontrib/`, installed into the backend virtualenv | Source unchanged. `backend/scripts/package_pg_contrib.py` builds against a disposable copy of the exact pinned wheel. `backend/scripts/install_pg_contrib.py` verifies and installs it offline. Bundles cover macOS arm64 (deployment target 14.0), glibc Linux aarch64 and x86_64 (manylinux 2.28), and Windows x64. The Linux and Windows bundles also replace the wheel's CPU-specific `vector` library with a portable build of the same source version: pgvector builds with `-march=native` everywhere but macOS ARM, so the wheel's library stops with an illegal instruction on a CPU that lacks its build machine's features (an x86_64 one without AVX-512, for instance). The manifest pins every installed file's checksum. Setup installs the bundle before migrating, with no compiler. The installer refuses an unsupported platform, a different wheel or PostgreSQL version, or a damaged bundle before it writes anything, and the runtime refuses to start without the required extensions. A new wheel or PostgreSQL source means rebuilding and validating every target: the hand-run `.github/workflows/pg-contrib.yml` builds each bundle on its own platform, and its Windows job also writes `launcher/windows/runtime-lock.txt`, which resolves only on Windows; `VERIFIED_UPSTREAM_VERSIONS` in `embedded_db.py` stops a dependency bump from skipping that. A bundle is executable third-party material: review its build inputs and validation evidence with the binary. |
